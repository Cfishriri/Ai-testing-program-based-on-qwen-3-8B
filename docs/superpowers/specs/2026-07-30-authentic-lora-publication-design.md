# Authentic LoRA Project Publication Design

## Goal

Publish a reviewable snapshot of the real `blockdata` LoRA training and evaluation project while preserving behavioral fidelity and removing only machine-specific or sensitive material.

## Publication strategy

Use a new branch, `agent/publish-authentic-lora-project`, based on the repository's remote `main`. Keep draft PR #1 unchanged. Open a separate draft PR after validation.

The published scripts must remain structurally and behaviorally equivalent to the active remote-workspace versions. Changes are limited to:

- replacing absolute server paths with command-line arguments, environment-backed configuration, or documented placeholders;
- removing secrets, credentials, private identifiers, and private dataset contents;
- adding minimal documentation, dependency metadata, safe sample data, ignore rules, and validation.

Training hyperparameters, Chat Template usage, label masking, LoRA configuration, checkpoint behavior, generation settings, answer extraction, and accuracy calculation must not be redesigned.

## Included scope

Inspect and include source files that participate in the current workflow, expected to include:

- `data_processor.py`
- `baseline.py`
- `lora-math-reasoning.py`
- `finetuned.py`
- `decode.py`
- `check_answer.py`
- `check.py`
- `simple agent.py`

Additional text source/config files discovered during inspection may be included when they are necessary to understand or run the project.

Add:

- a README describing the real workflow and every intentional sanitization;
- a dependency file derived from actual imports;
- a small synthetic data example matching the real processed schema;
- ignore rules for local environments, datasets, results, checkpoints, weights, caches, and editor state;
- lightweight source-contract validation.

## Excluded scope

Do not upload:

- `kv_cache_env` or any other environment;
- full training, validation, or test datasets;
- model weights or LoRA adapter weights;
- checkpoint directories;
- full `*_results.jsonl` or large error-sample outputs;
- caches, generated bytecode, editor settings, or credentials.

Generated configuration files may be included only if they contain no weights, credentials, private paths, or redundant information already represented by source code.

## Data and path handling

Absolute paths such as `/root/eb-public/...` and `/root/blockdata/...` will be replaced at the narrowest configuration boundary. The replacement must not alter downstream training or evaluation behavior.

Synthetic examples must preserve the real field contract—such as `input_ids`, `attention_mask`, and `labels` when those are the actual script inputs—without copying real dataset records.

## Validation

Before publication:

1. inspect every included file from the active VS Code workspace;
2. compare the sanitized version against the workspace version and record intentional differences;
3. parse all Python files;
4. scan uploaded text for credential patterns and absolute private paths;
5. verify that excluded artifacts are absent;
6. inspect the final PR filename list and CI result.

## Deliverable

A new draft pull request from `agent/publish-authentic-lora-project` into `main`, with a body that lists included files, excluded artifacts, sanitization changes, validation evidence, and any known limitations. Draft PR #1 remains unchanged.
